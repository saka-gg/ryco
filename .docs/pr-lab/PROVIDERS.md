# Pull Requests page: provider plan

The pull requests page (SPEC.md) runs on the change request contract (`packages/contracts/src/changeRequestReview.ts` and `sourceControl.ts`). This document plans how GitLab, Bitbucket Cloud, Forgejo (Gitea-compatible API) and Azure DevOps fill the parts of that contract only GitHub implements today. For every contract surface it gives the host call that backs it, the official docs, the auth scope, the field mapping, and the capability flag it unlocks.

## 0. How capabilities work

**One source of truth.** `getChangeRequestHostCapabilities(kind)` in `packages/shared/src/sourceControl.ts` (`@ryco/shared/sourceControl`) returns a `ChangeRequestHostCapabilities` for each provider kind. Each kind has its own delimited block in `CHANGE_REQUEST_HOST_CAPABILITIES` (`// ── gitlab ──` … `// ── end gitlab ──`), so one host's entry can change without touching another's.

- **Web.** `model.capabilities` (`PullRequestsModel`) gates every control. A control whose flag is false is hidden, not disabled. Reads the host cannot serve are never made, and facts the host does not send are never guessed: without `mergeReadiness` there is no verdict or merge control. Rows and the detail are separate: `listCheckRollup` and `listReadiness` (`verdict`, `blockers`, `none`) say what list rows carry, `checkRollup` and `mergeReadiness` what the detail carries. A `blockers` row names only the blockers it carries and otherwise reads "Open", never "Ready to merge"; a `none` row reads open, draft, merged or closed. `idleRefresh: "slow"` stretches the idle re-read of an open change request (5 min instead of 60 s) on hosts whose reads spawn many CLI processes.
- **Server.** `describeUnsupportedChangeRequestRequest(kind, request)` produces the one-sentence error. The ws handlers (`apps/server/src/ws/sourceControlRpc.ts`, `callSourceControlWorkflowMethod` in `ws/context.ts`) call `requireChangeRequestCapability` before the provider module loads. `withUnsupportedChangeRequestOptionGuards` applies the same matrix to the list, diff and create options for every other caller.
- **Flip a flag in the same change that implements it**, never ahead of it. Implementing it means:
  - provider code;
  - fixtures shaped exactly like the official response (cite the docs page in the fixture file);
  - provider tests;
  - the `enabledFlags` expectation in `packages/shared/src/sourceControl.capabilities.test.ts`.
- **No live writes.** Validate against recorded or hand-built fixtures only. There are no GitLab, Bitbucket, Forgejo or Azure accounts here.

**Consistency rules** (enforced by `sourceControl.capabilities.test.ts`):

- `activity` is a prerequisite for every mutation flag: `comment`, `reactions`, `editComments`, `deleteComments`, `lineComments`, `replyToThreads`, `resolveThreads`, any `submitReview.*`, a non-empty `lifecycle`, and any merge method. Viewer permissions (`ChangeRequestViewerCapabilities`), thread ids and comment ids all come from `getChangeRequestActivity`.
- `lineComments` needs `diff` and `submitReview.comment`.
- `commitDiffs`, `fileContents` and `viewedFiles` need `diff`.
- `workflowJobLogs` and `rerunWorkflows` need `workflowRuns`.
- `merge.deleteBranch` and `merge.expectedHeadSha` need at least one merge method.
- `create.draft` needs `create.supported`.
- `listCheckRollup` needs `checkRollup`; a `listReadiness` other than `none` needs `mergeReadiness` (rows never say more than the detail).
- `lifecycle.update-branch` is on exactly when `updateBranchMethods` (merge, rebase) is non-empty.

**Suggested order per host:**

1. `diff`.
2. `activity`, for reads: timeline, threads, viewer, `mergeReadiness`, `checkRollup`.
3. `comment` and `replyToThreads`.
4. `resolveThreads`.
5. `submitReview` and `lineComments`.
6. `lifecycle` kinds.
7. `merge`.
8. CI (`workflowRuns`, then logs, then reruns).
9. The rest.

**Thread shape every provider must produce** (`ChangeRequestReviewThread`):

- `side` is `left` for the base (deleted) side and `right` for the head (added) side.
- `line` is the current line on that side, or null once the thread no longer maps onto the diff. Then `isOutdated` is true and `originalLine` + `originalCommitOid` say where it was written.
- `startLine` / `startSide` are set only for range comments.
- `diffHunk` is a unified excerpt ending at the commented line (the timeline shows its last 4 lines).
- Ids are opaque, stable strings that round-trip into `replyToReviewThread{threadId}` and `setReviewThreadResolved{threadId}`. When a host needs a composite key, encode it (e.g. `discussionId`) and keep it reversible.
- Comment ids round-trip into `updateChangeRequestComment` and `addChangeRequestCommentReaction`.

**Viewer** (`ChangeRequestViewerCapabilities`) is derived per host from the authenticated user plus host permission data. When the host gives no permission bit, use the conservative value (false). The page then hides the control.

**Bodies never go through argv:**

- CLI providers stage them in a temp file (`withSourceControlBodyFile`): `glab api --field body=@file`, `az devops invoke --in-file file`.
- HTTP providers send JSON bodies.

## 2. GitLab (`glab` CLI + REST v4)

**Status: implemented** (provider `GitLabSourceControlProvider.ts`, page operations `gitLabMergeRequestPage.ts`, pure mapping in `gitLabApi.ts`, `gitLabMergeRequests.ts`, `gitLabMergeRequestActivity.ts`, `gitLabMergeRequestDiffs.ts`, `gitLabPipelines.ts`; fixtures from the docs' example responses in `gitLabMergeRequestPage.fixtures.ts`).

**Conventions:**

- Every call goes through `GitLabCli`: `glab` via `VcsProcess`, 30 s timeout, `LC_ALL=C`. Page calls use `GitLabCli.api` (`glab api --method <M> <endpoint>`) with the `projects/:fullpath/...` placeholder, so glab resolves the project from the checkout's remote; a merge request URL addresses its own project (URL-encoded path) and host (`--hostname`).
- **Bodies travel as JSON over stdin** (`--header "Content-Type: application/json" --input -`), never argv. `glab api --input` sends no content type of its own, and GitLab only parses a body declared as JSON. (The older `--field body=@file` route still serves `createMergeRequest`.)
- Lists are read page by page (`per_page=100&page=N`) up to a fixed budget; a short page ends the list, a full last page sets the `…Truncated` flag. `glab api --paginate` is not used (its output shape changed across glab releases).
- A failed call fails with GitLab's HTTP status on `GitLabCliError.status`, parsed from glab's `glab: <message> (HTTP <status>)` stderr and the JSON body on stdout; 404 on a file side means "absent", 409 on approve/merge means "head moved".
- Output is decoded with Effect Schema, per item for lists (one odd entry does not hide the rest).
- **Auth:** `glab auth login`. Token scope `read_api` for reads and `api` for writes ([token scopes](https://docs.gitlab.com/user/profile/personal_access_tokens/#personal-access-token-scopes)).

- `comment`, `editComments`, `deleteComments`, `lineComments`, `replyToThreads`, `resolveThreads`.

- `lifecycle`: `edit`, `set-draft`, `close`, `reopen`, `reviewers`, `labels`, `assignees`, `update-branch`, `auto-merge`, `delete-branch`; `updateBranchMethods`: `rebase` only (GitLab cannot merge the target branch in from its API, so "Update branch" rebases).
- `merge`: `merge`, `squash`, `rebase`, `deleteBranch`, `expectedHeadSha`.
- `checkout`, `create.draft`.
- Rows: `listCheckRollup`, `listReadiness: verdict`. `idleRefresh: slow` (the detail and activity are 6–8 `glab api` calls each).

**Off:** `reactions`, `viewedFiles`, `stacks`.

**Workflow runs:** the merged-results / merge-train head pipeline runs on a merge commit; its run carries `sourceHeadOid` (the head it verifies) so the Checks tab keeps it. A requested change is confirmed by re-reading `/reviewers` after `bulk_publish`, which answers 204 even when GitLab refused the reviewer state (no update rights, or not a reviewer and none can be added). Job logs stream through and only their last 1.6 MB is kept (`keepOutputTail`), so a long log's tail is its real end.

**Limitations:**

- Merge methods are per project; the detail's `mergeCapabilities` narrows the three to what the project allows.
- List rows carry mergeability, the merge-status verdicts and one pipeline, but not approvals, so a row blocked by something else (unresolved threads, rebase needed) can read as ready, as GitHub rows can.
- System notes are prose; unknown phrasings are dropped, never guessed.
- `diffHunk` and outdated state are derived; an outdated thread has no hunk.
- Request changes needs GitLab ≥ 19.2 (verify the exact release); approvals and drafts work on any release with the draft notes API (15.10+).
- `clientMutationId` (comment and reply idempotency) is not honoured.
- Image diff comments are not shown.

## 3. Bitbucket Cloud (REST 2.0)

**Status: implemented** (`BitbucketApi.ts`, `bitbucketPullRequestPageApi.ts` for the HTTP calls, `bitbucketPullRequestPage.ts` for decoding and mapping, `BitbucketSourceControlProvider.ts`). Fixtures: `bitbucketPullRequestPageFixtures.ts`. They copy the activity, commit, permission and merge-task examples from the docs; everything else follows the schemas in the [official OpenAPI document](https://dac-static.atlassian.com/cloud/bitbucket/swagger.v3.json).

**Conventions:**

- Effect `HttpClient` against `RYCO_BITBUCKET_API_BASE_URL` (default `https://api.bitbucket.org/2.0`).
- **Credentials** are resolved per call: a saved Atlassian connection (`bitbucket_token`, Basic `email:token`), else env `RYCO_BITBUCKET_ACCESS_TOKEN` (Bearer), else `RYCO_BITBUCKET_EMAIL` + `RYCO_BITBUCKET_API_TOKEN` (Basic).
- `executeJson` decodes with `HttpClientResponse.schemaBodyJson`; `executeText` handles diffs; `executeResponse` returns raw responses for 202/204/404/409 handling.
- Non-2xx responses become `BitbucketApiError{status, detail}`, which the provider maps to `SourceControlProviderError{provider: "bitbucket", operation}`.
- The repository comes from the remote (`resolveRepository` → `workspace/repoSlug`). Pull request, comment and thread ids must be numeric before any request is made.
- Bodies are JSON over HTTPS, never argv.
- Pagination follows the opaque `next` links ([REST intro](https://developer.atlassian.com/cloud/bitbucket/rest/intro/#pagination); `pagelen` is 10–100) with a cap per read:
  - activity: 5 × 50;
  - comments: 5 × 100, newest first;
  - commits: 3 × 100;
  - statuses: 2 × 100;
  - members: 5 × 100.
- Links that leave the configured API origin and path are refused, so credentials never follow them.
- Fork pull requests read head-side data (`src`, `diff/{sha}`, `commit/{sha}`) from `source.repository`.
- **Identity:** Bitbucket retired usernames, so a login is the account's `display_name` (falling back to nickname, account id, then uuid). List rows, timelines, reviewers and pickers all use it. `uuid` / `account_id` stay internal for matching (`sameBitbucketAccount`).
- **Heads:** pull request payloads abbreviate `source.commit.hash` to 12 hex characters.
  - The full head comes from the commit list, else `GET /repositories/{ws}/{repo}/commit/{hash}`.
  - Head guards compare by prefix (`bitbucketCommitsMatch`, at least 7 hex characters).
- **Scopes:**
  - API token scopes: `read:pullrequest:bitbucket`, `write:pullrequest:bitbucket`, `read:repository:bitbucket`, `write:repository:bitbucket` (branch deletion), `read:user:bitbucket` (`/user`, permissions), `read:workspace:bitbucket` (members).
  - Legacy app passwords: Account read, Workspace membership read, Pull requests R/W, Repositories R/W.
  - Reference: [API token permissions](https://support.atlassian.com/bitbucket-cloud/docs/api-token-permissions/).
  - Optional reads (permissions, statuses, mergeability, members) degrade to "unknown" when a scope is missing.
- **Rate limits:** each poll of an open pull request costs about 4–6 repository-data requests for the detail and 4 for the activity. Bitbucket's hourly limit on repository data can bite busy pages.

All pull request endpoints below are in the [pullrequests API group](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-pullrequests/) unless noted.

**Detail readiness.** Read from the pull request and its mergeability checks:

- `reviewerStates`:
  - `participants[].state` `changes_requested` → changes requested;
  - `approved` or state `approved` → approved;
  - role `REVIEWER` → requested;
  - plus any `reviewers[]` not already counted;
  - the author is excluded.
- `reviewDecision`:
  - any changes requested → `changes_requested`;
  - else a `standard_merge_check` with `check.kind` `minimum_approvals` (or the default-reviewer variant) decides: `PASSED` → `approved`, otherwise `review_required`;
  - else any approval → `approved`;
  - else none.
- `mergeability`: `git_mergeability_check.reason` `clean` → mergeable; `conflicts` or `merge_impossible` → conflicting.
- `mergeStateStatus`, first match wins:
  - conflicts → `dirty`;
  - draft → `draft`;
  - any blocking check other than the viewer-permission and state checks → `blocked`;
  - all passed → `clean`;
  - else `unstable`.
- `mergeCapabilities`: from `destination.branch.merge_strategies`.
- `deleteBranchOnMerge`: `close_source_branch`.
- `mergedBy`: `closed_by` when the pull request is merged.

**Activity timeline.** Update entries are snapshots of the pull request, so events are found by diffing successive ones:

- `title` → `renamed`;
- `state` → `merged` / `closed` / `reopened`;
- `draft` → `converted-to-draft` / `ready-for-review`;
- `destination.branch` → `base-ref-changed`;
- `reviewers` added or removed → `review-requested` / `review-request-removed`;
- a previous `source.commit` that is no longer one of the pull request's commits → `force-pushed`. This is only claimed when the commit list was read in full.

Other entries and their actors:

- `approval` → `review{approved}`; `changes_requested` → `review{changes_requested}`. The entry shape is taken from the approval example; the docs only name it, so verify the key against a live payload.
- Commits are ordered parents first, since dates tie after rebases.
- Top-level comments and their replies become `comment` items.
- The `author` on an update is the pull request's author, not whoever made the change, so update events have no actor. The exception is the final merge or decline transition, which takes `closed_by`.
- Truncating any read sets `timelineTruncated`.

**Activity threads.** A thread is an inline root comment plus every reply under it through the `parent` chain. Its `id` is the root comment id, which the resolve endpoint requires.

- `side`: `to` set → `right` (`line = to`); only `from` → `left`; neither → a file comment.
- Ranges: `start_to` / `start_from` set `startLine` / `startSide`.
- Outdated: `inline.outdated: true` (present in the docs' activity example) → `line: null`, `isOutdated`, with the original lines kept.
- Resolution: `isResolved` / `resolvedBy` from `resolution`.
- Deleted comments are dropped. `pending` comments (the viewer's unpublished drafts) show as `state: "pending"` and are not replyable or resolvable.
- Replies whose root fell outside the comment window are dropped and flag `reviewThreadsTruncated`.
- Permissions: only the viewer's own comments are editable. Resolving needs write access, authorship of the pull request, or authorship of the thread.
- `diffHunk` and `originalCommitOid` are not reported: the API has no commit for inline comments, and `context_lines` is undocumented.

**Review submit.** Bitbucket has no review object, so a review is a sequence of calls:

1. Validate every draft.
2. `GET` the pull request and require `expectedHeadSha` to match the head. Bitbucket anchors comments to the current diff and takes no commit.
3. Record the verdict, so a refused verdict (for example, approving your own pull request) posts nothing.
4. Post the line comments, then the summary.

The `reviewId` is the summary comment id, else the last line comment id, else `event:{participant uuid}`. `request_changes` needs no summary. Not atomic: if a later comment fails, the earlier ones stay. Pending comments cannot be published through the API, so `pendingReview` stays false.

**Merge.**

- Method → strategy, from `destination.branch.merge_strategies` (no settings call needed):
  - merge → `merge_commit`;
  - squash → `squash`, else `squash_fast_forward`;
  - rebase → `rebase_fast_forward`, else `fast_forward`.
  - A method with no allowed strategy fails.
- Only open pull requests merge.
- There is no head precondition parameter, so `source.commit.hash` is compared to `expectedHeadSha` right before the call. A narrow race remains, and Bitbucket's 409 covers refs that move during the merge.
- `close_source_branch` is sent only when `deleteBranch` is given.
- 555 → timeout error.
- Outcomes: a 200 pull request with state `MERGED` → `merged`; a task still `PENDING` after 30 polls 2 s apart, or a queued pull request → `enqueued`.

**Pipelines (not implemented).** Bitbucket Pipelines also publishes commit statuses, which the detail already reports as status contexts. The page would then list every run twice: as a workflow and as a status. Pairing the two needs the Pipelines status format, which is undocumented. Re-runs are full new pipelines (`POST .../pipelines` with the same `target`), so "Re-run failed" and "Re-run job" would claim more than they do until the web can say so.

**Entry today (`packages/shared/src/sourceControl.ts`):**

- `involvementFilters`, `search`, `activity`, `diff`, `commitDiffs`, `fileContents`.
- `comment`, `editComments`, `deleteComments`, `lineComments`, `replyToThreads`, `resolveThreads`.
- `submitReview`: `comment`, `approve`, `requestChanges`.
- `lifecycle`: `edit`, `set-draft`, `close`, `reviewers`, `delete-branch`.
- `merge`: all three methods, `deleteBranch`, and `expectedHeadSha` (pre-check).
- `checkout`, `create` + `create.draft`.
- Detail: `mergeReadiness`, `checkRollup` (the merge section and merge are shown).

**Limitations:**

- No reactions, labels, assignees, reopen, update-branch, auto-merge, publishing pending comments, viewed files or stacks.
- **Rows carry no readiness (`listReadiness: none`, `listCheckRollup` off).** The list endpoint has no mergeability, approvals or statuses, and one extra read per row would exhaust rate limits, so rows read open, draft, merged or closed.
- Workflow runs, job logs and re-runs (Pipelines) are not implemented; see above.
- The activity feed is coarse, so the timeline is rebuilt by diffing updates. The activity log's sort order is not documented: entries are sorted by date after reading, and a truncated read is assumed to drop the oldest entries (verify).
- Reviews are not atomic: a failing comment leaves the earlier ones posted.
- "Review requested" lists still include pull requests the viewer already approved.

## 5. Azure DevOps (`az` CLI + REST 7.1)

**Status: implemented** (`AzureDevOpsCli.ts`, `azureDevOpsPullRequests.ts`, `azureDevOpsPullRequestPage.ts` for pure mapping, `azureDevOpsPullRequestOperations.ts` for calls; fixtures in `azureDevOpsPullRequestPage.fixtures.ts` are copied from the official examples in [MicrosoftDocs/vsts-rest-api-specs](https://github.com/MicrosoftDocs/vsts-rest-api-specs) `specification/<area>/7.1/httpExamples`, the source of the "Sample response" blocks on learn.microsoft.com).

**Conventions:**

- Every call goes through `AzureDevOpsCli.execute`: `az` via `VcsProcess`, 30 s timeout, `LC_ALL=C`; JSON reads add `--only-show-errors --output json`; `--detect true` resolves org/project/repo from the remote.
- **Endpoints with no `az repos` command** go through `AzureDevOpsCli.invoke` → [`az devops invoke`](https://learn.microsoft.com/en-us/cli/azure/devops?view=azure-cli-latest#az-devops-invoke) `--area <area> --resource <resource> --route-parameters k=v… --query-parameters k=v… --http-method … --api-version 7.1 --in-file <tmp.json>`. Resource names are the `x-ms-vss-resource` values of the REST spec (`pullRequestThreads`, `pullRequestThreadComments`, `pullRequestIterations`, `pullRequestIterationChanges`, `pullRequestCommits`, `pullRequestLabels`, `pullRequests`, `refs`). Route parameters are the project **id**, the repository **id** and the pull request id from `az repos pr show`.
- **`az devops invoke` cannot parse `-preview.N` versions** (it converts the version to a float), so preview endpoints use `-preview`; the policy read uses `az repos pr policy list` instead of the preview REST version.
- **Bodies never travel on argv:** REST bodies are staged in a temp JSON file for `--in-file`; CLI descriptions use Azure CLI's `@file` expansion (`--description @tmp.md`). `AzureDevOpsCli.executeWithFile` removes the file afterwards.
- **Local git** (`AzureDevOpsCli.runGit`, `GIT_TERMINAL_PROMPT=0`): Azure has no REST endpoint that returns hunks ([Diffs - Get](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/diffs/get?view=azure-devops-rest-7.1) lists paths only). Missing commits are fetched by id (`git fetch <remote> <sha>…`), falling back to `refs/pull/<id>/merge` (its parents are the last test merge's target and source) plus the source and target branches.
- **Head:** `lastMergeSourceCommit` is the head Ryco reports, because it is what completion checks. Review comments anchor to the latest iteration, so a review requires `iterations[latest].sourceRefCommit == expectedHeadSha`.
- **Auth:** `az devops login` (PAT) or `az login` (Entra). PAT scopes: Code (Read & write) `vso.code_write` (threads, votes, completion, refs, labels), Project and Team (Read) `vso.project` + `vso.profile` (reviewer candidates), Work Items (Read) `vso.work` (tag candidates); the Has Permissions call lists no scope in the reference (**verify** for PATs) ([scopes](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/oauth?view=azure-devops#scopes)).

**Limitations:**

- No hunk diffs over REST: diffs and contents need the server's checkout and a fetchable remote.
- Likes are the only reaction; no assignees, update-branch or pending reviews.
- Completion is policy-driven and asynchronous; auto-complete has no head precondition.
- No check rollups or CI yet (`checkRollup`, `workflowRuns` false).
- Points marked **verify** could not be confirmed without a live organization: `Location`/`Profile` areas for `invoke`, Git permission bit values, the `StatusUpdate` thread properties, PR labels in the tag store, and the `pullRequests` location `invoke` resolves.

## 6. Unknown hosts

There is no provider, so every flag stays false. `describeUnsupportedChangeRequestRequest("unknown", …)` names "This source control provider". The page shows a list error and no reader controls.
